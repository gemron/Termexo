## 微信通知无发送验证

设置页默认关闭、目标为文件传输助手，完成/错误/授权默认勾选，输入提醒默认不勾选。微信 4.1.15.13 最初在 `SelectionItemPattern.Select()` 报错；后续已适配实际搜索项形态和动态分组，改为 Invoke/Select 加界面回执核对，必要时用经过 UIA 矩形、RuntimeId 命中及前台进程校验的原生点击打开唯一搜索项。

最终真实 Tauri 设置页中，文件传输助手和现有群均通过完整“不发送”预检，包含精确标题、空且可写的输入框、唯一发送按钮及 InvokePattern。现有群通过“最常使用”分组和原生点击回退打开。真实联系人查询出现“查看全部”时拒绝；不存在目标也拒绝。自行建立的固定草稿使检查拒绝，返回微信确认内容未改变后仅清除此测试草稿。纯解析测试另覆盖重名、跨类型重名、聊天记录排除、大小写和未知分组，共 14 个夹具；未修改用户联系人制造重名。通知保持关闭，没有发送任何消息。

事件收集、范围过滤、恢复抑制和持久化占位去重已通过自动化测试；后端投递测试使用模拟 transport 验证超时不重试及跨数据库连接占位，不能当作微信发送成功的证据。本机打开目标及发送前检查已通过，真实发送链路尚未验证。若用户后续明确授权，固定验证方案为向“文件传输助手”仅发送一次“Termexo 通知测试。”；本轮未执行该方案。

## Codex 启动状态、手动空闲与授权横幅复查

新建 Codex 没有 nativeSessionId，前端原先在 PTY 启动后把它默认设为 RUNNING。现在新建与恢复的 Codex 都进入 IDLE，仅在仍为 STARTING 时应用；启动期间已收到的工作、审批、输入、错误等状态不会被覆盖。后端 Codex SessionStart 原本已归一为 session.ready；补充过滤晚到的启动就绪事件，避免覆盖已经开始的任务，同时让 IDLE 也能启动既有的启动对话框及任务投递计时器。PTY 普通输出不产生通用 RUNNING 回写。

运行中或思考中的终端在状态旁提供“设为空闲”。它通过现有状态保存入口更新终端及关联任务，不写入 PTY、不发中断、不结束进程、不标记完成；时间戳过滤旧事件，后续真实事件正常生效。等待审批、输入、错误及结束状态不提供此入口。常用操作由运行状态防止重复启动服务，因此不提供手动改为空闲，以免启动重复服务。IDLE 不触发完成微信通知。

授权横幅是正文流中的独立行，却使用了高于终端标签栏的层级，覆盖了标签栏内部的外观等下拉。已移除该横幅不必要的层级，没有全局抬高菜单。1100×720 原生窗口使用本次自建会话的模拟授权显示事件，验证外观下拉及字体列表可展开、可点选，同时授权横幅仍可读；没有批准任何真实操作。截图：`native-approval-dropdown-fixed.png`。

真实新 Codex 会话在没有输入任务时显示空闲；通过应用 MCP 接口分开输入和提交“Only reply READY. Do not use tools, read files, run commands, or modify anything.”，实际观察到 IDLE → THINKING → COMPLETED 并得到 READY。随后用仅改变显示的模拟工作事件实测“设为空闲”，Codex PID 前后均为 27752，输入及进程未被中断；后续模拟审批事件正常更新状态。该自建测试终端已关闭。

前端完整 740 项通过，后端完整 439 项通过、4 项忽略，嵌入生产前端的原生 debug 构建通过，diff 检查通过。本轮没有修改 Rust 行为，没有重打正式安装包；此前 0.10.15 安装包不包含本节修复。微信保持关闭且未发送消息，没有提交、推送或发布。
