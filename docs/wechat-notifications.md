# Windows 微信桌面通知

顶部“远程访问”旁提供独立的[第三方通知总开关](third-party-notifications.md)。微信是其中一个渠道：实际发送需要总开关和微信渠道开关都开启。总开关暂停时保留微信的全部配置。

在「设置 → 微信通知」配置。默认关闭，目标默认为“文件传输助手”。可填写完整联系人或群名称，选择全部或指定项目，以及任务完成、错误/限流、等待授权、等待输入事件。等待授权只发送提醒，不执行审批。

通知使用已登录的 Windows 微信主窗口，通过 UI Automation 搜索和核对目标，不依赖微信接口或网页登录。需要唯一的主窗口、空搜索框、无聊天草稿、唯一且类型明确的精确搜索结果，以及可操作的聊天输入框和发送按钮。重名、版本不兼容或标题变化时停止，并显示失败原因；不按坐标猜测目标。

微信最小化或收进托盘时，发送前枚举微信进程所属的顶层窗口，不再依赖最小化时可能为零的 `Process.MainWindowHandle`。优先识别唯一可见主窗口（包括最小化窗口）；全部隐藏时用 `MainView` 区分已登录主界面和隐藏登录窗口。恢复并前置后，等待窗口坐标连续四次稳定，才检查草稿、搜索目标及填写消息。已有正常或最大化窗口不会被改为普通大小；登录窗口、多个主窗口、弹窗阻挡或无法切到前台时停止。发送按钮也会等实际点击位置不再被其他原生窗口遮挡后才开始稳定计数。

最小化恢复和隐藏窗口重新发现均已在本机以不发送模式验证：恢复到前台、按钮检查通过、草稿保持原样。通知记录中的失败原因包含恢复窗口、检查草稿、搜索目标、等待按钮、点击前校验或确认消息等阶段，便于定位中断位置。

随后经用户授权，从最小化状态运行完整生产 `desktop.ps1`，向文件传输助手发送指定测试文字。窗口恢复、搜索目标、填写内容、原生点击和新消息确认全部通过：输入框清空，消息列表新增一条完全匹配的消息。此测试覆盖完整桌面自动化脚本，未伪造任务事件或修改既有通知历史。

“检查目标（不发送）”可能切换聊天，但不填消息、不点击发送。检查通过不代表发送已验证。发送后只有在微信消息列表中看到完整消息且输入框清空，才记为“已提交”；这不代表网络最终投递或对方已读。若发送后无法确认，记为“结果不确定”，不会自动重试。

消息使用第三方渠道共用的内容模板，包含通知时间（本机日期时间及 UTC 时区偏移）、项目、任务，以及可用的会话、Agent、模型和分支信息；缺失的可选信息省略。通知时间与投递记录的创建时间一致，读取本机时区失败时明确显示 UTC。末尾按任务完成、错误/限流、等待授权、等待输入给出相应处理提示，不附终端日志。启动时恢复的状态、历史事件、普通 Shell、常用操作长期进程、账号登录终端不触发通知。关闭时发生的事件不会在启用后补发。每次尝试先写入数据库，再操作微信；事件键通过数据库原子占位防止同一事件跨进程重复发送。最近 50 条结果在设置中显示。

支持范围取决于微信版本暴露的可访问性模式。当前适配器接受文件传输助手的功能搜索项，以及“联系人”“群聊”“最常使用”分组中名称与 AutomationId 一致的搜索项；聊天记录、收藏和网络结果不作为目标。联系人/群结果出现“查看全部”时拒绝继续，因为无法排除隐藏的重名目标。实际发送需要在目标机器上单独验证，不能仅凭单元测试或目标检查宣称可用。

2026-10-24 的本机原生检查发现，微信 4.1.15.13 的 `SelectionItemPattern.Select()` 可能报错。当前搜索流程使用经过核对的原生点击：等待唯一精确搜索项及其所属窗口坐标连续四次稳定，点击前重新核对搜索文字及结果身份，点击后等待搜索弹层消失、完整聊天标题连续三次匹配，才允许填写消息。不使用固定坐标或盲点。

微信搜索结果可能位于独立的 `Qt…QWindowToolSaveBits` 原生弹层。只有该弹层与微信主窗口属于同一进程、且直接由主窗口拥有时，才用弹层作为搜索项点击的窗口边界。其他进程、无关窗口、非搜索弹层、截断结果及重名目标均拒绝；该处理仅用于搜索结果，发送按钮仍要求属于主窗口。实机已从其他聊天开始运行完整“不发送”检查，成功切回配置的文件传输助手、核对完整标题和空输入框，全程未输入或发送消息。

发送不再依赖可能没有实际效果的 `InvokePattern.Invoke()`。填入通知后每 150 毫秒重新读取唯一发送按钮，要求可见、启用、边界位于父元素及微信窗口内，且按钮、父元素和窗口坐标连续 4 次相同；至少等待约 600 毫秒，最多等待 6 秒。稳定后只执行一次原生点击，鼠标移到按钮后再等待 150 毫秒重新核对，按下保持 60 毫秒后释放。点击瞬间再次核对完整聊天标题和草稿原文；成功需要输入框清空且出现本次新增的消息元素，同文历史消息不算成功。点击后无法确认时记录为结果不确定，不自动重试；现有草稿及用户中途修改的内容均保留。

2026-10-25 本机定位发现，微信有时报告落在窗口外的旧按钮坐标，且 `AutomationElement.FromPoint()` 可能只返回微信窗口，无法下钻到按钮。适配器拒绝无效边界并等待坐标稳定；只有命中正确按钮，或者 UIA 只返回唯一微信根窗口且 Win32 `WindowFromPoint` 也确认同一个根窗口时才允许继续。命中其他控件、窗口、进程或弹窗均拒绝。整体自动化进程超时为 30 秒，覆盖搜索、稳定等待及发送确认。

同日先通过了不移动鼠标、不点击、不改草稿的实际定位检查，随后经用户明确授权，使用生产 `Wait-SendButton` 和 `Verified-Click` 逻辑向文件传输助手发送现有 Termexo 通知草稿一次。实测只点击一次、输入框清空、消息列表新增一条与草稿完全一致的消息，界面提交确认通过。该验证没有覆盖从新任务事件开始的完整自动通知流程，也未改写原有通知历史。

真实 Tauri 设置页检查已通过默认文件传输助手和一个现有群的完整预检：目标唯一、聊天标题精确、输入框可写且为空、发送按钮唯一并暴露 InvokePattern。现有群验证了“最常使用”分组及原生点击回退；联系人查询的截断结果、不存在目标和已有草稿均拒绝继续。自建草稿检查后内容保持原样，并仅清除了该测试草稿。重名及跨类型重名由纯解析夹具覆盖，未修改真实联系人制造重名。全程没有发送消息，通知保持关闭；实际发送仍未验证。

MCP 的「设置」权限组提供 `wechat_notification_status`、`wechat_notification_probe` 和 `wechat_notify`。AI 无法通过这些工具启用通知或修改目标；发送必须符合用户保存的开关、事件类别和项目范围。远程浏览器不能调用这四个桌面通知后端命令。
